# Week 4 - Activity and swimlane diagrams

## Problem

Map the professor workflow and its handoffs to the student interface.

## Relevant Context

The activity and swimlane diagrams established how the request moves between the student, system, professor and notifications.

## Key Observation

The interface needs to reflect changes made by another user. I mapped visible status changes to outcomes confirmed by the system.

## Solution

I worked through the approval, rejection and rescheduling branches of the activity and swimlane diagrams. I identified where the professor sees a request, where the system returns an updated state, and where the student sees the resulting status or notification. I included feedback for an unavailable slot so the student can return to availability and choose again. The workflow defined how both interfaces should respond to decisions and scheduling changes.

## Next Steps

Identify which data the navigation, slot lists and status views require.
